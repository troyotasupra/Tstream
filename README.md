# Tstream

Streams audio out of a DAW over UDP — a ReaStream-style network audio sender — plus a
**standalone receiver app** that plays the stream back through any Windows audio endpoint.

The pair exists to solve a specific problem: **a DAW running on ASIO is invisible to
screen-sharing apps.** ASIO bypasses the Windows audio engine entirely, so Discord, Zoom and
anything else that captures process or system audio can never hear your DAW, no matter what
you share. Tstream taps the master bus, sends it over loopback UDP, and the standalone
renders it through WASAPI — where those apps *can* reach it.

```
REAPER master ──► Tstream VST3 (send) ──UDP:9200──► Tstream standalone (receive) ──► Windows endpoint
                                                                                        │
                                                                          Discord screen-share audio
```

Point the standalone at an output you can't hear (a monitor's HDMI audio endpoint with
nothing plugged into it works well) and viewers hear your DAW while you don't hear a
duplicate. Share whatever you like on screen — the audio path is independent of what is
being shared visually.

This replaces the older [TstreamOBS](https://github.com/troyotasupra/TstreamOBS) plugin,
which did the same job but required running OBS purely as an audio renderer.

## The standalone app

- **Output Device** — the endpoint the stream is rendered to. Shared-mode WASAPI only;
  exclusive mode is reported as a warning, because it bypasses the Windows mixer and would
  make the audio uncapturable.
- **Output Level / MUTE** — a fader for what listeners hear, independent of the DAW's master.
- **Listen On** — an optional second output on its own device, so you can monitor what is
  being sent without it sharing the streaming device.
- **Input Device** — used only in SEND mode; the capture device is released whenever the app
  is not sending, so it never holds an interface a DAW wants.
- **PIN** — keeps the window above the DAW.
- Settings persist on change, so a crash doesn't cost you the setup.

The VST3 can start the receiver automatically: with **Auto-start receiver app** enabled, a
plugin instance in send mode launches the standalone if one isn't already running.

### Sample rates

The receiver resamples, so the stream rate and the output device rate are allowed to differ
— which matters because WASAPI shared mode locks a device to the endpoint's Default Format
in Windows. A 44.1 kHz project into a 48 kHz endpoint plays at correct pitch.

The resampler also does drift correction. Sender and receiver run on independent hardware
clocks that never tick at exactly the same rate, so a fixed buffer inevitably walks to one
end — underrunning or overflowing — and no buffer size prevents it, because it is a rate
mismatch rather than a jitter problem. The correction is applied as a sub-0.5% deviation on
the resampling ratio, spread across every sample, which is inaudible.

## Building

Requires the [JUCE](https://juce.com) SDK and Visual Studio 2022 (Windows only, for now).

```
cmake -B build -G "Visual Studio 17 2022" -A x64 -DTSTREAM_JUCE_DIR="C:/path/to/JUCE"
cmake --build build --config Release
```

The VST3 installs to `%LOCALAPPDATA%\Programs\Common\VST3` and the standalone to
`%LOCALAPPDATA%\Programs\Tstream` automatically after building. Prebuilt copies of both are
in [`dist/`](dist).

The application icon is generated by [`Assets/make_icon.py`](Assets/make_icon.py) (standard
library only — no Pillow or ImageMagick required).
